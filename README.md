# 웹 기반 병원 관리 시스템 (Web-based Hospital Management System)

3학년 1학기 '웹 서버 프로그래밍' 강의에서 배운 Node.js(Express), MongoDB, Pug/HTML 기술을 활용하여 병원 행정 절차(병원 등록·승인, 역할 기반 접근 제어, 병실 시각화 및 입·퇴원, 의료진 스케줄 및 진료 예약, 환자 차트 관리, 자동 DB 백업)를 하나의 웹 플랫폼으로 통합 구축한 관리 시스템 프로젝트입니다.

> 본 프로젝트는 2025년도 3학년 1학기 과제물로, 취업 포트폴리오 관리를 위해 로컬 컴퓨터에 보관 중이던 소스코드를 깃허브 레포지토리로 이관한 프로젝트입니다.

---

## 1. 프로젝트 소개
* **진행 기간:** 2025.04 ~ 2025.06 (약 2개월)
* **개발 배경 및 목적:**
  * 병원 내 파편화된 행정 업무(병원 등록, 소속 승인, 병실 배정, 환자 진료 기록, 예약 관리)를 단일 웹 플랫폼으로 통합하여 운영 효율성을 극대화합니다.
  * 서버 관리자, 병원 관리자, 의료진, 환자로 이어지는 **역할 기반 접근 제어(RBAC)** 및 계층별 승인 파이프라인을 구축하여 의료 데이터 보안을 강화합니다.
  * HTML을 활용하여 층수와 호수에 따른 2D 병실 배치도를 동적으로 시각화하고, 환자 입·퇴원 상태를 실시간으로 관리합니다.
  * Node.js 백엔드 환경에서 비동기 데이터 처리, Nodemailer 이메일 인증, 스케줄러 기반 정기 DB 백업 등 실무 수준의 백엔드 운영 아키텍처를 설계합니다.

## 3. 디렉토리 구조

```text

```

## 4. 시작 가이드 및 실행 방법

### 📌 환경 변수 설정 (`.env`)
프로젝트 루트 경로에 `.env` 파일을 생성하고 아래의 환경 변수를 설정합니다.

```env
# 1. 서버 및 세션 설정
SESSION_SECRET=your_session_secret_key
NODE_ENV=development

# 2. 몽고DB 접속 정보
MONGO_URL=mongodb://localhost:27017
DB_NAME=hospital_db

# 3. 이메일 인증용 계정 및 앱 비밀번호
EMAIL_USER=your_email@gmail.com
EMAIL_PASS=your_gmail_app_password

# 4. 문자 발송용 Twilio API 정보
TWILIO_SID=your_twilio_account_sid
TWILIO_AUTH_TOKEN=your_twilio_auth_token
TWILIO_PHONE_NUMBER=your_twilio_phone_number
```

### 📌 설치 및 서버 구동

```bash
# 1. 의존성 패키지 설치
npm install

# 2. 로컬 서버 실행 (기본 포트 3000)
npm start
```
*(서버가 실행되면 `http://localhost:3000`으로 접속할 수 있으며, `utils/backup.js` 백업 스케줄러가 백그라운드에서 자동 구동됩니다.)*

## 5. 시스템 아키텍처 및 권한 체계

### 🏗️ 시스템 아키텍처
* **MVC & Router 분리 설계:** `routes`를 통해 요청 경로를 세분화하고, 미들웨어(`middlewares`)를 통해 4단계 권한을 사전 검증한 뒤 `controllers`와 `models`를 거쳐 DB 트랜잭션을 처리합니다.
* **4계층 권한 모델 (RBAC):**
  1. **서버 관리자 (Server Admin):** 신규 병원 등록 승인/반려, 병원 관리자 권한 승인, 병원 정보 수정/삭제 승인, 정기 데이터베이스 백업 모니터링.
  2. **병원 관리자 (Hospital Manager):** 소속 병원 정보 등록/수정 신청, 소속 신청 의료진 승인, 병실 생성 및 전체 입·퇴원 현황 총괄.
  3. **의료진 (Doctor / Staff):** 진료 스케줄 등록 및 캘린더 관리, 환자 신규 등록 및 진료 차트 작성/수정, 병실 배정 및 실시간 입·퇴원 처리, 환자 진료 예약 승인/반려.
  4. **환자 (Patient):** 등록된 병원 및 의료진 검색, 의료진 스케줄 기반 진료 예약 신청/취소.

```text
[클라이언트 요청] 
       │
       ▼
 [Express Router] (app.js)
       │
       ▼
[보안 미들웨어] ──▶ 세션 유효성 검증 (isLoggedIn) 
                  ▶ 권한 검증 (ensureServerAdmin / ensureManager / ensureDoctor)
       │
       ▼
  [Controller] ──▶ 비즈니스 로직 처리 및 데이터 가공
       │
       ▼
 [Mongoose Model] ──▶ MongoDB 트랜잭션 및 영구 저장
       │
       ▼
 [View / JSON] ──▶ Pug SSR 렌더링 & REST API JSON 응답
```

## 6. 주요 기능 및 모듈

* **인증 및 계정 승인 시스템 (`routes/auth.js`, `middlewares/`):**
  * 병원 도메인 이메일 기반 유효성 검증 및 Nodemailer를 통한 6자리 보안 인증번호 발송.
  * bcrypt를 활용한 비밀번호 단방향 암호화 저장.
  * 가입 후 즉시 권한이 부여되지 않고, 상위 관리자의 승인을 거쳐야 활성화되는 2차 검증 흐름 적용.
* **2D 캔버스 기반 병실 시각화 및 입·퇴원 관리 (`routes/room.js`, `public/`):**
  * 병실 번호에서 층수(floor)와 호수(roomNumber)를 파싱하여 HTML5 Canvas 상의 좌표를 동적 계산.
  * 병상 수용 인원 및 현재 입원 환자 수에 따라 캔버스 색상을 동적으로 변경 (녹색: 여유, 황색: 혼잡, 적색: 만실).
  * 캔버스 클릭 이벤트를 감지해 다이얼로그를 띄우고, 환자 검색 후 즉시 입원 및 퇴원 처리.
* **의료진 스케줄 및 환자 예약 엔진 (`routes/schedule.routes.js`, `routes/reservation.routes.js`):**
  * FullCalendar UI를 연동하여 의료진의 진료 가능 시간대 등록 및 직관적 시각화.
  * 환자의 예약 신청 시 기존 승인된 일정과의 중복 여부를 백엔드에서 검증하여 타임슬롯 충돌 원천 차단.
* **환자 전자의무기록(EMR) 차트 관리 (`routes/patient.js`):**
  * 로그인된 의료진의 소속 병원 ID와 의료진 ID를 차트 폼에 자동 바인딩.
  * 환자 인적 사항 및 문진·진단 내용, 복약 기록을 통합 문서 형태로 저장 및 관리.
* **자동 백업 및 시스템 복구 체계 (`utils/backup.js`):**
  * 서버 구동 시 백업 스케줄러가 백그라운드에서 동작하여 주기적으로 DB 스냅샷을 생성하고 데이터 무결성 보장.

## 9. 트러블 슈팅 및 문제 해결 과정

### 1. 뷰 렌더링 방식의 불일치 (Pug 템플릿과 정적 HTML 혼재)
* **문제점:** 프로젝트 초기 프론트엔드 렌더링 컨벤션을 확립하지 못해 팀원별로 Pug(SSR)와 정적 HTML(`public/`)을 혼용하여 개발하면서 디렉토리 구조와 렌더링 방식에 혼선이 발생했습니다.
* **해결방안:** `app.js`에서 `app.set('view engine', 'pug')`로 템플릿 엔진을 마운트함과 동시에 `app.use(express.static('public'))`를 적용하여 두 방식이 충돌 없이 서빙되도록 라우팅 경로를 정비했습니다.

### 2. 외부 SMS 문자 발송 API 통합 한계
* **문제점:** 진료 예약 확정 알림을 환자 SMS로 전송하는 기능을 기획하여 단독 테스트 스크립트에서는 동작을 확인했으나, 메인 서비스 서버 환경으로 이식하는 과정에서 외부 통신 연동에 실패했습니다.
* **원인 및 개선점:** 무료/테스트용 SMS API의 발신 번호 인증 제약과 웹 서버 비동기 트랜잭션 내 타임아웃 예외 처리가 미흡했음을 분석했습니다. 이를 통해 외부 서드파티 통신은 메인 서비스 로직과 강결합하지 않고 비동기 메시지 큐(Message Queue)나 백그라운드 워커 형태로 격리 설계해야 함을 체득했습니다.

### 3. Canvas 병실 배치도 좌표 계산 및 MongoDB ObjectId 매핑 오류
* **문제점:** 병실 목록을 캔버스에 그릴 때 층수/호수가 어긋나 화면 밖으로 이탈하거나, MongoDB의 `ObjectId` 타입과 클라이언트에서 전달받은 병원 ID 문자열이 불일치하여 병실 조회가 실패하는 현상이 발생했습니다.
* **해결방안:** 병원 식별자를 표준 문자열로 통일하고, 병실 번호에서 층수(`Math.floor(room / 100)`)와 호수(`room % 100`)를 분리 연산하여 그리드 좌표 `(x, y)` 오프셋을 동적으로 계산하도록 알고리즘을 개선했습니다.

### 4. 세션 만료 후 비인가 접근 및 브라우저 캐시 보안 결함
* **문제점:** 세션 유효 시간이 만료된 후에도 브라우저 뒤로가기나 새로고침 없이 이전 화면에서 버튼을 클릭할 경우 비정상적인 데이터 요청이 발생할 수 있는 보안 취약점이 있었습니다.
* **해결방안:** 모든 민감한 API 및 화면 라우터 진입점에 `isLoggedIn`, `ensureManager`, `ensureServerAdmin` 미들웨어를 배치하여 세션 상태를 실시간 재검증하고, 만료 감지 시 경고창 팝업 후 즉시 로그인 페이지로 강제 리다이렉트되도록 조치했습니다.

### 5. AI 증상 기반 진단 추천 기능의 법적 한계로 인한 기획 변경
* **문제점:** 초기 기획에서 환자의 증상을 입력받아 진료과를 추천해 주는 AI 모듈을 구상했으나, 의료법상 비의료인의 진단 보조 기능 적용에 대한 규제 이슈가 확인되었습니다.
* **해결방안:** 서비스의 법적 안정성을 확보하기 위해 해당 기능을 과감히 제외하고, 핵심 의료 행정 프로세스인 환자 EMR 차트와 의료진 스케줄 예약 시스템 고도화에 집중했습니다.

### 6. 초기 네이밍 컨벤션 및 모듈 인터페이스 미표준화로 인한 통합 병목 현상
* **문제점:** 각 팀원이 개별 모듈을 분담 개발하는 과정에서 변수명, 파일명, API 응답 데이터 규격에 대한 사전 협의가 부족하여 메인 라우터로 통합할 때 대량의 데이터 불일치 및 라우팅 충돌 에러가 발생했습니다.
* **해결방안:** 총괄 리더로서 전체 코드를 전수 검수하여 변수 네이밍 규칙과 MongoDB 식별자 포맷을 통일하고, 흩어져 있던 라우트와 컨트롤러 매핑 구조를 일원화하여 모듈 간 데이터 정합성을 확보했습니다.

## 10. 프로젝트를 통해 배운 점 및 향후 개선 사항
* **역할 기반 권한 분기 및 미들웨어 설계 역량:** 사용자 역할(Admin, Manager, Doctor, Patient)에 따라 백엔드 라우팅 및 세션을 제어하는 보안 아키텍처의 중요성을 깊이 체득했습니다.
* **협업 컨벤션의 필수성:** 프로젝트 초기 뷰 렌더링 표준(Pug vs HTML)을 통일하지 않고, 변수명, 파일명 등을 협의하지 않아 발생했던 구조적 복잡성을 경험하며, 개발 착수 전 인터페이스와 기술 스택 표준화의 중요성을 배웠습니다.
* **향후 개선점:**
  * **프론트엔드 단일화:** 혼재된 Pug와 HTML 구조를 React/Vue 등의 모던 SPA 프레임워크 또는 단일 SSR 템플릿으로 통합 마이그레이션.
  * **메시징 파이프라인 분리:** 신뢰도 높은 클라우드 SMS API(AWS SNS, Twilio)를 메시지 큐 기반 비동기 파이프라인으로 재구축.
  * **실시간 세션 동기화:** WebSocket을 도입하여 세션 만료 시 새로고침 없이도 즉시 클라이언트 화면을 로그아웃 상태로 전환하는 실시간 동기화 구현.
